# minibot A2A Agents Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Add Agent2Agent (A2A) protocol support to minibot so it can discover, delegate to, and collaborate with remote agents as first-class tools, while also exposing minibot itself as an A2A-compliant agent.

**Scope:** Implement A2A v1.0.0 JSON-RPC 2.0 over HTTP/REST (not gRPC in this phase). Agent Cards at `/.well-known/agent.json`, Task lifecycle management, synchronous + streaming (SSE) message exchange. Reuse existing minibot AgentLoop / AgentRunner / ToolRegistry instead of adding a separate orchestration layer.

**Key Principle:** A2A is for agent-to-agent collaboration; MCP is for agent-to-tool communication. minibot already has MCP — this plan adds A2A as a complementary layer.

## Architecture

```text
minibot local agent
    → tools/a2a_client.py (A2AClientTool)
        → HTTP/JSON-RPC to remote agent endpoint
        → Remote Agent (A2A-compliant, any framework)
    ← api/routes/a2a.py (A2AServer)
        ← Remote Agent or Client (JSON-RPC calls)
        ← AgentLoop / AgentRunner / ToolRegistry
```

- **Outbound**: new builtin tool `a2a_call` lets minibot delegate subtasks to remote agents
- **Inbound**: new FastAPI router `/a2a/*` exposes minibot as an A2A server
- **Discovery**: `GET /.well-known/agent.json` + `POST /a2a/v1/agent-card` for capability advertisement
- **Task state**: A2A Task objects map to minibot Sessions (1:1 for simple turns, N:M for long-running goals)

## Dependencies

- Python 3.11+
- httpx (already in minibot)
- pydantic (already in minibot)
- No extra SDK required for the JSON-RPC over HTTP binding; can add `a2a-sdk` later if spec stabilizes

- `minibot/src/minibot/api/routes/a2a.py` (new router)

**Implementation:**
1. Build `AgentCard` from minibot settings:
   - name: `minibot.local` or `MINIBOT_SERVER_A2A_AGENT_NAME`

   - inputModes: `["text/plain", "application/json"]`
   - outputModes: `["text/plain", "application/json"]`
2. Add endpoints:
   - `GET /.well-known/agent.json` → returns card
   - `GET /a2a/v1/agent-card` → same (JSON-RPC style alias for some clients)
3. Dev UI: extend `/ui/` or `runtime.html` with "A2A Card" link

**Verification:**

## Task 3: A2A Client Tool (Outbound Delegation)

**Files:**
- `minibot/src/minibot/agent/tools/a2a.py`
- `minibot/src/minibot/a2a/client.py`

**Implementation:**

   - `discover(url) → AgentCard`

3. Register tool in `register_default_tools()`
4. Add Dev UI `/ui/a2a.html` for testing outbound calls:
   - form: agent URL, message, task_id
   - display: task status timeline, artifacts, errors

**Verification:**

## Task 4: A2A Server (Inbound Task Handling)

**Files:**
- `minibot/src/minibot/api/routes/a2a.py`
- `minibot/src/minibot/a2a/server.py`

**Implementation:**
1. Add JSON-RPC 2.0 router `/a2a/v1/` with methods:
   - `message/send` → create task, run AgentLoop turn, return Task
   - `message/sendStreaming` → SSE stream of task status updates
   - `tasks/get` → query task state
   - `tasks/cancel` → abort task
   - `tasks/resubscribe` → reattach SSE stream
   - `pushNotifications/set` / `get` / `list` → optional webhook config
2. Map A2A Task → minibot Session:
   - `task.contextId` → `session_id`
   - `task.id` → unique A2A task id (prefix `a2a_`)
   - `message.parts` → user text for `loop.handle_turn()`
   - runner output → `artifacts` (text parts)
   - tool calls → `history` entries with `part_type: "data"`
3. Reuse session lock: A2A tasks on same `contextId` serialize like normal chat
4. Dev UI: extend `runtime.html` to show active A2A tasks with `entry_path: "a2a"`

**Verification:**
- `curl -X POST http://127.0.0.1:8766/a2a/v1/message/send -H "Content-Type: application/json" -d '{"jsonrpc":"2.0","id":"1","method":"message/send","params":{"message":{"role":"user","parts":[{"type":"text","text":"hello"}]}}}'` returns valid Task JSON
- Same task `contextId` continues conversation across multiple A2A calls
- SSE stream emits `status` + `artifact` events

## Task 5: Streaming + Task Persistence

**Files:**
- `minibot/src/minibot/a2a/store.py`
- `minibot/src/minibot/api/routes/a2a.py`

**Implementation:**
1. Add in-memory + JSONL-backed A2A task store:
   - `~/.minibot/a2a_tasks/<task_id>.jsonl`
   - mirror session store patterns
2. On `message/sendStreaming`, bridge `AgentRunner.run_stream()` events to `TaskStatusUpdateEvent` / `TaskArtifactUpdateEvent`
3. Map minibot stream events:
   - `delta` → `artifact.parts` append
   - `reasoning_delta` → `artifact.metadata["reasoning"]`
   - `tool_call_start` / `tool_result` → `history` entries
   - `stream_end` → `status: completed`
   - `error` → `status: failed`
4. Persist task state after each update so `tasks/get` works mid-stream

**Verification:**
- Restart minibot, `tasks/get` for completed task still returns full history
- SSE client can reconnect and resubscribe to same task

## Risks / Open Questions

1. **Task vs Session granularity**: A2A allows one contextId to have many tasks. minibot sessions are chat-oriented. Should one A2A contextId map to one session with many turns, or many sub-sessions? Current plan: 1 contextId → 1 session, N tasks → N turns. Revisit if long-running goal support needs sub-session isolation.
2. **Streaming bridging complexity**: A2A SSE requires specific event shapes. minibot stream events are internal. Need careful translation to avoid leaking implementation details.
3. **Tool naming collision**: If remote agent also exposes tools, minibot's `a2a_call` could conflict. Mitigate by prefixing tool name with `a2a_` and logging remote agent URL in call metadata.
